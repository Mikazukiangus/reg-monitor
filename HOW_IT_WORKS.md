# How RegSonar Gets Its Data

For local setup and deployment settings, see [`CONFIGURATION.md`](./CONFIGURATION.md)
and the complete [`.env.example`](./.env.example).

RegSonar has no special access or data agreements. Every notice and figure comes from a public page or feed that the regulator itself publishes, and the server reads it the same way a browser would.

## The flow of a sync

1. **A server on Vercel (Hong Kong region, `hkg1`) fetches each source.** The site's own Express server (`server.ts`) does the fetching, not the visitor's browser and not any AI service. Each source is fetched at most once every 10 minutes when someone visits. Separately, a scheduled check reads every source every three hours (see "Keeping every source up to date" below).
2. **Each item is put into a common format:** title, regulator, date, link, type and so on.
3. **Key points are quoted from the document itself** (`server/summarize.ts`). For each notice, the server opens the linked document once (key points already in the history are reused, so a new server instance doesn't read the documents again) and picks its most central sentences word for word using TextRank, a ranking algorithm, not an AI model. It also picks out sentences containing dates and reference numbers. Scanned PDFs are read with Tesseract OCR (the first 4 pages), and those quotes are labelled "OCR". A PDF over 15 MB or 1,000 pages, or a scanned page image over 40 megapixels, is not read, so its notice shows no key points rather than key points from part of it (`server/extract.ts`); the largest documents the sources linked in October 2026 were 6.5 MB and 471 pages. Chinese and Japanese documents are split into sentences at "。" and quoted as published, not translated.
4. **Each notice is saved to the history database** (`server/db.ts`, Postgres on Neon) when a database is connected. See "Notice history" below.
5. **Vercel's CDN keeps a copy** of the combined result for up to 5 minutes. Visitors get it instantly, and "Data as of" shows when it was built. A refresh (the Sync button, or a copy older than 10 minutes) skips the CDN; the server then reuses a result it built in the last minute, and each visitor may refresh 6 times a minute (after that the server answers HTTP 429 and the page says when to try again; see Rate limits below). Both limits are kept per server instance.
6. **The visitor's device keeps its own copy** (`public/sw.js`) for offline use.

### Data privacy

These come from the data protection authority of each jurisdiction RegSonar already covers. A privacy regulator's own news is kept whole, less speeches, events and procurement notices. Feeds that also cover other work (the FTC's and the OAIC's, and China's policy library) keep only items about privacy or personal data (`shared/privacyTopics.ts`: English, Chinese and Japanese words for it, and abbreviations such as GDPR and PDPA in capitals). Every notice from these sources is tagged "Data privacy"; one that is also about AI rules (an AI and personal data consultation, a fine for automated decision-making) is tagged "AI rules" too. Data privacy is also a sector, "Data Privacy & Protection" (link key `privacy`), with its own filter and Radar row. Privacy words give it (the same words as above, from any source), and every notice from a data protection authority is in it, even when its words give other sectors too ("Complaints about automated nuisance calls" is Conduct and Data Privacy); "Why these tags?" then says the regulator is a data protection authority. On 15 October 2026 privacy was briefly part of the AI sector's name ("AI, Data Privacy, Cyber & Tech Risk"); bookmarks and offline copies saved under that name are read as "AI, Cyber & Tech Risk" and refreshed from the feed when shown. A link or saved view with only some sectors ticked lists them by key, so one made before the new sector doesn't include it; tick it and save the view again to add it. One with every sector ticked has no list and includes it.

## What the site works out itself

These come from rules in the code, not from the regulators:

- **Impact score and severity:** one rubric for every source, described below.
- **Sector and format:** assigned by keyword rules in `shared/tagging.ts`, described below.
- **Dates:** taken from the source's own date fields where there are any (the Federal Register's comment and effective dates, MAS's and SGX's consultation closing dates). Otherwise from a sentence in the document that states a date for the document itself, and every date says what kind it is:
  - **Comments close:** a request for comments with its date ("Comments should be submitted by 30 November 2026"), or, on a consultation only, a statement such as "The consultation closes on 14 October 2026". A digest or event notice can mention another paper's closing date, so there the general statement is not used.
  - **Takes effect:** "will take effect on", "become effective on", "the effective date ... is", "shall apply on". Not used on consultations, where the date is only proposed.
  - **Comply by:** an obligation with a date ("should have ... in place by 1 July 2030").
  - The cue must come right before the date, so another date in the same sentence is not taken for it ("gazetted on 16 October and become effective on 1 November" gives 1 November). Sentences about proposals, conditions or views ("proposed", "would", "if", "differing views") give no effective or compliance date, a date being replaced ("instead of 1 January 2027") is skipped, and enforcement actions and digests take no dates from their text.
  - **The date shown** (one per notice, `shared/keyDate.ts`) comes from the regulator's dates if it published any, else from the document's: the closing date if comments are still open, else the soonest upcoming date it takes effect or must be complied with (not on consultations or enforcement actions), else a closing date that has passed, shown as "Comments closed: 2026-10-13". A date the regulator published that has passed is shown as "Took effect: 2026-10-06" or "Comply by: 2026-09-01 (passed)"; a passed date from the document's text is not shown on the card (it stays in the dossier's timeline). A notice with no date shows none: Federal Register notices without a comment or effective date no longer say "No date published". The sentence a date came from is shown with the notice's dated statements and on hover.
  - Notices store only the dates themselves: those the regulator publishes (`sourceDates`) and those the document states (`keyPoints.dates`). Which one is shown, and whether it has passed, changes from day to day, so it is worked out each time a notice is shown, on the day in Hong Kong, by the same function for the cards, the horizon, calendar files, the email digest, exports and the impact score. Copies stored before 21 October 2026 have the date they showed as text instead (`statutoryDeadline`); the regulator's date is read back from it, and the old fields are not served.
  - The rules are tested on sentences from real notices (`tests/dates.test.ts`, `tests/key-date.test.ts`). Dates from the text are worked out again whenever a stored notice is read, so a rule change applies to the whole history.
- **Consultation links:** a consultation is linked to its outcome published later by the same regulator, and back, when their titles share most of their topic words (`shared/related.ts`). An outcome is conclusions, a response to the consultation or its feedback, a decision to proceed, a final version, or a PRA policy statement (PS19/26, answering CP6/26); words such as "amendments", month names and document numbers don't count as topic words. Regulators don't publish this link in a form a program can read, so it is labelled "matched by title". The links are stored in the history (`notice_links`): a notice the feed reads is matched against its regulator's whole history when it is saved, and each scheduled check matches the whole history again once it has saved what it read (it doesn't match each source's notices on the way), so a change to the rule reaches every notice within hours. Every notice the site serves shows its links: the feed, history search, shared links and saved notices. Without a history, the notices at hand are matched with each other. `tests/fixtures/related-sample.json` holds 727 production notices with the pairs that should link and some that must not; `npm test` checks that the rule makes exactly those links.

## Keeping every source up to date

A visit refreshes each source's newest 3 or 4 items, so a regulator that publishes more than that between visits, or a source added later, would otherwise have gaps. To close them:

- **Scheduled check** (`/api/feeds/poll`): Vercel cron jobs call it every three hours (03:00, 06:00 … 21:00 UTC; the 00:00 digest does the same check). The Hobby plan allows each cron job to run once a day, so there are seven daily jobs at different hours, and Vercel may start each one up to an hour late. It needs `CRON_SECRET`, like the digest: at least 32 characters (e.g. `openssl rand -hex 32`), compared in constant time; without one, or with a shorter one, both jobs are off (503, and a shorter one is logged as a warning) and the rest of the site is unaffected (`server/routes/cron.ts`, `tests/cron-auth.test.ts`).
- It reads the newest 20 items of every source and saves them to the history. If none of those 20 is in the history yet (a new source, or more than 20 items published since the last check), it reads back 50.
- It adds key points to up to 5 documents per source per run, newest first, so a backlog is worked through over the next few runs without hammering any site.
- When it finishes it requests the public feed, so the copy Vercel's CDN serves visitors includes what it found.
- **Rate limits:** requests to FINRA are spaced 4 seconds apart. After an HTTP 429 (too many requests) from any site, the server doesn't ask that site again for as long as its Retry-After header says, or 15 minutes.

## Notice history

Most feeds only list their latest 10 to 50 items, so without a store older notices drop out of view. When the Vercel project has a Postgres database (Neon, added in the project's Storage tab, which sets `DATABASE_URL`), the server saves every notice it reads, with its key points, after each successful refresh. The feed then also shows notices from the last 30 days that are no longer in the live feeds, marked "From history", and the search box searches the whole history by title, summary and key points. Without a database the site works from the live feeds alone.

The history part of the feed is capped at 1,000 notices (`ARCHIVE_FEED_LIMIT`, see `CONFIGURATION.md`); notices that are also in the live feeds don't count towards it. The cap is a safeguard, not the usual stop: in October 2026 the 30 days held about 300 history notices. Until 21 October 2026 the cap was 300 and counted the live notices too, so the feed's "last 30 days" reached back only about 20 days and shrank as more was published. If the cap is reached, the oldest notices of the 30 days are left out and the server logs a warning.

The database is connected to Production only. Branch preview deployments have no database: they show the live feeds as read from Vercel's Hong Kong region, without history or scheduled-check results, the same as local development. This is deliberate, for two reasons. Every refresh saves notices, so a preview with production's database would write a branch's untested results into the history. And Neon's Free plan allows 10 database branches per project, so a database copy for each preview filled the limit within about a day and stopped every preview from deploying ("Resource provisioning failed", October 2026).

**Changing the database's tables.** The tables are set up by numbered migrations in `server/migrations.ts`. When the server connects, it applies any the database hasn't had yet, in order and in one transaction, and records each in a `schema_migrations` table, so each runs once. If one fails, none of that run's changes are kept, and the site carries on without history until it is fixed. Server instances that start together take turns, so a migration never runs twice. To change a table, add a migration at the end with the next number; don't edit one that has run, because databases that already have it won't run it again (the server logs a warning if its text changes). Previews have no database, so a new migration first runs on production when its branch is merged: test it with `npm test`, which runs every migration on an empty database and on one made before migrations.

**Indexes.** Besides the primary keys, the history has indexes for the queries the server sends (`server/db.ts`): publication date (the feed's last 30 days), full-text search, regulator id, source, consultation links by outcome, dates by day, and two partial ones (migration 5): undated notices by when they were last seen (the scheduled check's date backfill) and completed scheduled checks by when they finished (the check status). At about 1,100 notices every query the feed and search send takes under a millisecond; the scheduled check's rebuilds of links and dates read every notice by design. Measured on copies of the production notices at 50,000 notices, the undated notices take 0.24 ms instead of 10.5 ms, and the last completed check reads one index entry instead of sorting every check. An index on the regulator name was tried and left out: linking a regulator's notices spends its time reading two fields out of each notice's JSON, not finding the rows. `npm test` checks that the two queries use their indexes.

**Checking requests.** Every API route declares the methods and query parameters it accepts (`server/validate.ts`), and a request is checked against them before the route runs: another method gets 405 with an `Allow` header; a request body gets 400 (no route takes one, so none is parsed); an unknown, repeated, missing or invalid query parameter gets 400. Messages are fixed and never repeat what was sent. Query values are always text, never objects built from names such as `q[a]`. Searches are 2 to 200 characters (the page cuts longer ones), notice ids a JSON list of 1 to 50, digest days real calendar days, and `dryRun` only `1` or `0`, so a mistyped `dryRun=true` is refused instead of sending the real email. Any other `/api` address gets a JSON 404, and the cron secret is compared in constant time. In the browser, saved alert rules and the notices seen on the last visit are checked before use, as saved notices, saved views and the feed reply already were. `tests/validation.test.ts` checks each of these. Settings are checked when the server starts (`config.ts`); data from regulator sites is checked by each source's parser and the recorded-reply tests, and by the page when the feed arrives.

**No markup from outside the page.** Text from regulators, searches, shared links and what this browser saved is shown by React, which escapes it; nothing is inserted as HTML (no `dangerouslySetInnerHTML`, `innerHTML` or `eval`), and the digest email escapes every field. The one way such text becomes active is a link, so a notice's links (its source, the document its key points quote, and linked consultations or conclusions) are kept only when they are web links: plain HTTP is upgraded to HTTPS, and anything else (`javascript:`, `data:`, a relative or malformed address, or one with control characters) is dropped and the notice shown without that link. The server checks them when it tags a notice (`server/notice.ts`) and links notices (`shared/related.ts`), and the page checks them again in the feed, search and saved-notice replies (`withSafeLinks` in `src/lib/noticeShape.ts`) and before opening a linked notice at its source. The Content Security Policy runs no inline script except the theme script's hash, as a last guard. `tests/safe-urls.test.ts` checks each of these.

**Which pages may call the API (CORS).** The site's own page is on the same origin as `/api` (on Vercel both are served from one address, previews included; locally Express serves the page through Vite), so it needs no CORS headers. Every `/api` reply goes through `server/cors.ts` first: a request without an `Origin` header (Vercel's cron jobs, curl, the page's own GETs) or from the site's own origin goes on as before; an origin listed in `CORS_ALLOWED_ORIGINS` gets `Access-Control-Allow-Origin` with that exact origin, preflights for GET, HEAD and POST, and no credentials or extra headers (so a browser can never send the cron secret); any other origin, `null` included, gets 403 "Origin not allowed" before the route runs. The list is empty by default and takes exact origins only (HTTPS, or HTTP on this machine; no wildcards, paths or `*`). Replies carry `Vary: Origin`, so Vercel's CDN keeps a separate cached copy per origin. The page's static files keep Vercel's default `Access-Control-Allow-Origin: *`; they are public and carry no credentials. `tests/cors.test.ts` checks each of these.

**Rate limits.** Every `/api` request is counted per visitor (IP address) before its route runs (`server/rate-limits.ts`), after the origin check. Per minute: 6 refreshes (`POST /api/feeds/sync`, `REFRESH_LIMIT`); 10 calls to the scheduled jobs (`/api/feeds/poll`, `/api/digest`), which slows down guessing `CRON_SECRET`; 30 searches, 30 by-id lookups and 30 endpoint-status reads (the database, or every regulator site when the instance's copy is over 5 minutes old); and 120 of anything else (the cached feed, health, checks, rules). Over a limit the API answers 429 with `Retry-After` and "Too many requests. Try again in N seconds." (the Sync button's own message for refreshes), never cached. The limits are well above what the page uses (about four uncached calls on load, an auto-sync every 3 minutes mostly from the CDN, search 400 ms after typing stops) and leave room for an office sharing one address. They are kept in each server instance's memory, at most 10,000 addresses per limit (those seen longest ago are forgotten first), so on Vercel each instance counts separately; replies from Vercel's CDN cache never reach them. A limit across all instances is a Vercel Firewall rule (Hobby allows one): Project → Firewall → Configure → New Rule, If Request Path starts with `/api`, Then Rate Limit, Fixed Window, 60 s, 300 requests, key IP, action Default (429); Review Changes → Publish. It runs before the CDN cache and the function. `tests/rate-limits.test.ts` checks each route's limit.

**Only public addresses are read (SSRF guard).** Visitors never give the server an address to read: the API takes no URLs. But the server does read addresses it did not choose, namely links in regulators' feeds, PDF links found on their pages, and wherever those redirect. Every such request goes through `politeFetch` (`server/http.ts`), which accepts HTTPS only and connects through `server/ssrf.ts`. When each connection is made, the host name is resolved and every address it resolves to must be on the public internet. Refused are private ranges, loopback, link-local (including the cloud metadata service at 169.254.169.254), carrier-grade NAT, documentation, benchmarking, multicast and reserved ranges, and the IPv6 equivalents, including IPv4 written as IPv6 and NAT64 or 6to4 addresses that can lead to IPv4. The connection then goes to that checked address, with TLS still verified against the host name. Because the check runs at connection time, every redirect hop is checked, an address written oddly (`https://0x7f000001/`, `https://2130706433/`) is caught after the URL parser reads it, and a name that resolves differently a moment later (DNS rebinding) cannot slip through. A refused request fails with "Refused <host>: <address> is not a public internet address", shown as that source's error. The guard uses the `undici` package (Node's own HTTP client) for its connection hook. Two requests to fixed addresses are not guarded: the digest email to Resend, and the scheduled check's request for the site's own feed (`DIGEST_SITE_URL`, which is `localhost` when run locally). `tests/ssrf.test.ts` makes real connections to check each of these, including a redirect from an allowed site to a private address.

**Every outbound call has a time limit.** Regulator sites: 8 seconds for the whole reply (`FETCH_TIMEOUT_MS`, `server/http.ts`); a slow DNS lookup in the SSRF guard ends with it. The digest email to Resend: 15 seconds (`RESEND_TIMEOUT_MS`). The scheduled check's request for the site's own feed: 30 seconds (`FEED_WARM_TIMEOUT_MS`). The database (`server/db.ts`): 10 seconds to get a connection, whether Neon is waking up or the pool is busy (`DB_CONNECT_TIMEOUT_MS`), and 30 seconds for each query's answer (`DB_QUERY_TIMEOUT_MS`). The query limit is the client's: the query is reported as failed but runs on in Postgres, because Neon's connection pooler may refuse `statement_timeout` as a connection setting. The page (`src/api/client.ts`, `WAIT_MS`): 60 seconds for the feed, which may read every source; 30 for endpoint status; 20 for search, saved-notice lookups, digest rules and scheduled-check status. A feed that does not answer in time says "The feed server did not answer within 60 seconds." The service worker (`public/sw.js`) waits for the network at most 10 seconds for pages and public files and 50 for the feed, then answers with the saved copy while the request carries on and still updates it; with no saved copy it keeps waiting. `tests/timeouts.test.ts` checks each limit, including a real connection to a database that never answers.

**Retries, only where repeating is safe.** A call that fails for a reason likely to pass is tried again, up to 3 tries in all (`RETRY_ATTEMPTS`), pausing about 0.5 s and then 1.5 s, each at random between half and one and a half times that (`RETRY_BASE_DELAY_MS`, `server/retry.ts`). A `Retry-After` up to a few seconds is honoured; a longer one is not waited for. Regulator reads (`politeFetch`, `server/http.ts`): GET requests, and the ICO's news search, a POST that only reads (`readOnly`), are tried again after a dropped connection (`ECONNRESET`, `EPIPE`, `ETIMEDOUT`, `EAI_AGAIN`, a closed socket) or HTTP 502, 503 or 504. A refused connection, an unknown name, a certificate error, any other status (403 bot blocks, 404, 500, 429, which pauses the site as before) and the 8-second time limit are final, so a slow site still costs one time limit. Each try keeps the site's spacing and 429 pause. The digest email (`server/mailer.ts`) carries an `Idempotency-Key` made for that send and kept on every try, so Resend sends it at most once; it is tried again on 429, 5xx, 409 `concurrent_idempotent_requests`, a dropped connection or its 15-second time limit, and any other refusal is final. Database queries are not retried (a write or transaction could be applied twice); a failed connection is tried again by the next request. The page and service worker do not retry: the feed syncs every 3 minutes and the service worker falls back to the saved copy. Each retry is logged ("trying again in … ms"). `tests/retry.test.ts` checks each rule.

**Circuit breakers for sites and the database.** A regulator site that fails 3 times in a row (`BREAKER_FAILURES`) is not asked again for 5 minutes (`SITE_BREAKER_COOLDOWN_MS`, `server/breaker.ts`). A failure here means a timeout, a network error (refused, reset, unknown name, certificate) or an HTTP 5xx; a retried call counts once. Its sources show "Not asked: … failed 3 times in a row (last: …); asking again after HH:MM UTC" until then. After the cooldown one request is let through as a trial: if it works the site is asked as usual, if not it waits another cooldown. Any other answer, a 404 or 403 included, shows the site is up and starts the count again. A 429 has its own pause, as before. Without this, a site that stops answering costs a full 8-second time limit for every document page on it, one after another. The endpoint status check always asks the site, so the status page stays current, and a site that answers it is asked as usual again. The history database has its own breaker: after 3 failed connections or queries in a row (time limits, broken or refused connections, but not errors the database itself reports), the history is treated as off for 30 seconds (`DB_BREAKER_COOLDOWN_MS`) instead of each request waiting 10 seconds to connect. Resend and the scheduled check's own feed request have no breaker: each is called once per run, hours apart, so there is nothing to cut short. Breakers are kept in memory, per server instance, like the rate limits.

**What visitors are told when something fails.** Source errors in the feed, endpoint status details and the scheduled check's summary are public, so they carry only messages written for visitors (`server/errors.ts`): a site's HTTP status, "Timed out after 8s", "Network error: ECONNREFUSED", a reply that was not what the source expects (`SourceError`), and the app's own refusals (plain HTTP, a private address, a site's 429 pause, a circuit breaker). Any other error, such as a database error or a bug in a parser, is shown as "Failed (details in the server log)", and the full error goes to the log. API routes already answer with fixed messages. A scheduled job that is turned off answers "Scheduled jobs are unavailable", whether `CRON_SECRET` is missing or too short; the reason goes to the log only. On the page, a history search that fails, or an endpoint check that fails, says so, rather than looking like no matches or leaving the old statuses without a word. The scheduled check logs a warning when its request to refresh the public feed fails.

**Concurrent updates.** Several server instances write to the history at once: a scheduled check on one, visitors' refreshes on others. Every write is a single statement, and where code reads data, works on it and writes it back, the update is made atomic:
- **Rebuilds and visitor saves.** The scheduled check works out every notice's dates (`notice_dates`) and consultation links (`notice_links`) again and replaces them. A visitor's refresh saves a new notice's dates and links meanwhile. Each rebuild reads and replaces in one transaction holding its own advisory lock (`pg_advisory_xact_lock`; dates and links have one each, `server/store.ts` `exclusive`). A visitor's save takes the same lock, so it waits and is written after the rebuild, instead of being deleted by it.
- **Page dates.** The page-date backfill reads a stored notice, reads its page for a few seconds, and then writes only what it learned, merged into the row as it is then (`patchNotice`). It used to write its whole copy back over a newer save. A date is set only if the notice still has none.
- **Saving notices.** Notices are saved in id order, so two saves that share notices lock their rows in the same order and cannot deadlock.
- **Browser storage.** Saved notices, saved views and alert rules are changed from what is stored now, not from the tab's own copy, so a change made in another tab is kept. Each tab follows the others' changes (the `storage` event). Saving or removing a notice applies what the person asked for, so it cannot undo another tab's change by toggling.

In-memory caches already share one request while it runs (`reuseFor`, the endpoint status cache, a source's refresh), and migrations already run under their own advisory lock.

**Background jobs.** Work nobody should wait for runs from a queue kept in the history database (the `jobs` table, migration 6; `server/queue.ts`), so it outlives the request that asked for it:
- **Reading documents for key points.** A visitor's refresh used to read every new document before answering, 13 to 15 seconds on a new server instance. Now it answers with the source lists, adds the key points already stored, and queues one `key-points` job per document not read yet. Those run after the response has been sent, for up to a minute (Vercel's `waitUntil`, read from the request context rather than adding `@vercel/functions` and its two dozen dependencies). The next feed build shows the key points they stored. The scheduled check still reads its share of documents itself, so the digest it feeds is unchanged, and queues the rest instead of leaving them to the next check. A document read with too little text to summarise (a page that only points to an attachment, say) is marked in the history (`noKeyPoints`, kept when its source saves the notice again and left out of what the site serves), so it is not queued or read again by any server instance; documents don't change once published.
- **Sending the digest.** The daily run queues the email and sends it straight away. If Resend cannot take it, the run answers 202 and the send is tried again after 5, 15 and 45 minutes, then about 2 and 7 hours, all with one idempotency key, so it is never sent twice. A day's digest already sent is not queued again.

A job waiting is listed once per kind and key. A worker takes a job for 150 seconds, longer than a function may run, so a job left by a stopped worker is taken again. Workers on other instances skip jobs already taken (`FOR UPDATE SKIP LOCKED`). Failed jobs wait longer each time (key points: 15 minutes, 1 hour, 4 hours) and give up after their last try. Every scheduled check also runs due jobs until 75 seconds after it started, and removes finished jobs older than a week (those that gave up, a month). The Source freshness panel shows how many are waiting and how many gave up this week. Without a database there is no queue, and documents are read in the refresh as before.

These stay in the request: reading the source lists (they are the answer, about 2 seconds), saving notices (quick), the endpoint status checks (cached for 5 minutes), and the scheduled check's own work (it is already a background run).

**HTTPS everywhere.** The site is only served over HTTPS: Vercel answers plain HTTP with a permanent redirect (308) to the same address over HTTPS, and every reply carries `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` (set in `vercel.json`, the same as Vercel's own default) and a Content Security Policy with `upgrade-insecure-requests`. The site sets no cookies. Nothing the page loads names a plain-HTTP address (the page, scripts, styles, manifest, service worker; Google Fonts over HTTPS). The server reads regulator sites over HTTPS only, refusing a plain-HTTP address and a reply a redirect brought from one (`server/http.ts`); a notice's links are shown over HTTPS (`safeUrl` in `shared/urls.ts`); the site address in emails is HTTPS except on this machine. `tests/https.test.ts` checks each of these. Run outside Vercel, HTTPS, the redirect and these headers must come from the server in front of the app.

**Queries per request.** Reads are batched: a feed build whose sources are still fresh sends 3 queries (the last 30 days, the history's count, and the links of every notice shown in one query), a search 2, and a lookup by id 2 (the page asks for bookmarks 50 at a time). Writes go source by source. When the feed refreshes a source it reads the stored copies of what it listed, saves them with the source that read them in one statement, stores their dates, and for consultations and outcomes matches them against their regulator's history. A scheduled check does the first two for each source, using the stored copies it reads once both to see what is new and to reuse key points, and then works out the dates and links of the whole history once; on the recorded replies of 51 sources it sends about 105 queries. `npm test` checks that a check reads each source's stored copies once and does not work out dates or links per source.

**Dates in SQL.** Every date a notice has is also stored in the `notice_dates` table (migration 4), one row per date: whether the regulator published it or the document states it, its kind (`closes`, `takesEffect`, `complyBy`), the sentence that states it, and whether a closing date is stated generally. It is filled when the feed saves notices, and each scheduled check, once it has saved what it read, works out every notice's dates again and stores exactly those (its log gives the count), so a rule change reaches the table within hours. The site itself doesn't read the table. `sql/upcoming-deadlines.sql` lists the upcoming date each notice shows, soonest first, by the same rule as the site; on a copy of 757 production notices it gave the same 110 dates. Two rare cases can differ: a document that states two closing dates (the site takes the first it states, the query the soonest still ahead), and a notice whose format rules changed since it was last saved.

**Sources and regulators.** Each source has a stable id (`server/sources/index.ts`, such as `hkma-circulars`) that stays the same if its display name changes. Every save records which source read each notice in the `notice_sources` table, with when it first and last did; one document can come from more than one source (the Federal Register and its AI search, MAS's three searches, and China's two policy-library searches share id prefixes). Notices saved before October 21, 2026 were linked to their source by id prefix where only one source uses it; the rest are linked the next time a source reads them. The scheduled-check log names each source by its id too. Each regulator has a stable id in `shared/regulators.ts` (such as `us-sec`), set on every notice as `regulatorId` and stored in the `regulator_id` column, so the history can be grouped by regulator even after a display name changes. A regulator name that isn't listed still gets an id made from the name, and the server logs it once so it can be added.

**How notices are named.** A notice's id is its key in the history and in saved and shared links, so it must name the same document every time it is read, and only that document. Each source builds it from something the regulator publishes: a reference number (SFC, ASIC, the Federal Register's document number) or the last part of the document's link. A link with no path ("…/?p=123") is named by its query. Where a source gives neither, the id uses a short hash of the document's link or title (Federal Register documents without a number, ASX entries without a PDF, Japan's Cabinet Office and PPC), never its place in a list, which would hand the id to another document once the list moves. Saving a list that names one notice twice keeps the first copy. The scheduled check logs a warning when an id it reads is already saved with a different link. `npm test` checks that every notice in the recorded replies keeps the id listed in `tests/fixtures/notice-ids.json`: a change to how ids are made must not rename notices already saved.

## Other things that use the same data

- **Status checks:** every 5 minutes, each source gets a single request to see whether it is up, slow, or blocked by a firewall or maintenance page. This feeds the "sources up" count.
- **Email digest** (`server/services/digest.ts`, rules in `digest-rules.ts`): a Vercel cron job runs each morning at about 08:00 Singapore time. It runs the scheduled check below and emails the site owner, through Resend, the previous day's notices that match the rules. No email is sent on days with no matches. It needs `CRON_SECRET`, `RESEND_API_KEY` and `DIGEST_TO` in the Vercel project settings (see `.env.example`).

## Sectors and formats

Each notice gets up to three of twelve sectors: Banking & Prudential; Capital Markets & Listings; Funds & Asset Management; Insurance & Pensions; FinTech, Payments & Digital Assets; AI, Cyber & Tech Risk; Data Privacy & Protection; ESG & Sustainability; AML/CFT & Financial Crime; Conduct & Consumer Protection; Monetary & Financial Stability; General & Institutional.

- **Whole words only.** "AI" no longer matches inside "maintain", and "fund" doesn't match "own funds" or "guarantee fund". Regulator names are removed before matching, so "Monetary Authority" doesn't make a notice about monetary policy, and "Bank of England" doesn't make it about banks.
- **The title counts most.** A word in the title scores 3; a word in the summary or key points scores 1. A sector needs 3, so the summary alone can add a sector only when several of its words appear.
- **Ties** go to the more specific topic (for example AML before Banking). For market regulators and exchanges, Capital Markets goes first.
- **No topic words:** market regulators and exchanges default to Capital Markets & Listings, the PRA and Basel Committee to Banking & Prudential, everyone else to General & Institutional. The notice says that the tag is a default.
- **Format** (Consultation, Enforcement, Guidelines, Technical Standards, else Circular) also comes from phrases in the title, checked in a fixed order: speeches and approval orders are never enforcement or consultations; "orders", "no-action letter" or "suspended companies" alone don't make a notice enforcement.
- **Reasons are kept.** Every notice records the words that gave each tag, and the card shows them under "Why these tags?".
- **Old notices are re-tagged** when read back from the history, so a rule change applies to everything shown.

Quality checks:

- `tests/tagging.test.ts` holds hand-labelled notices taken from the live sources, with the sector and format a reader would give them. A rule change that breaks one fails the tests.
- `npm run tags:review` reads the live sources and lists the notices whose tags rest on the weakest evidence: defaults because no topic words matched, sectors that came from the summary only, and circulars by default. Reading that list now and then shows rules that are missing. When a tag is wrong, add the notice to the test file with the right answer, then change the rules until every test passes.

## Impact score

Every notice gets its score from one function, `shared/impact.ts`, the same way for every source and for notices read back from the history. Before this, each source set a fixed number per format and the Federal Register used its own scale, so a routine SEC paperwork notice scored "High" while a final MAS circular scored "Info", and notices kept whatever score they were stored with.

What the document does (the first that applies):

| Kind | Score |
| :--- | :--- |
| Routine: data releases, events, appointments, speeches, cooperation agreements, periodic reports, paperwork notices | 3 |
| An exchange's or SRO's rule filing published by the SEC | 4 |
| Other circulars and announcements | 5 |
| Technical standards | 6 |
| Guidance | 6.5 |
| Enforcement action | 7 |
| Consultation open for comment | 7 |
| Rules made: final rules, amendments (including amendment regulations and directions), policy statements, consultation conclusions, requirements taking effect | 7.5 |

Dates move it, by the date the notice shows: +1.5 when comments close within 14 days or rules take effect within 30 days (a date the regulator publishes, such as the Federal Register's effective date, or a "Takes effect" date from the document's text; a "Comply by" date does not move the score); a consultation whose closing date has passed scores 4. Days are counted from today in Hong Kong, as the dates shown are. Severity follows the score: Critical from 8.5 (so only something with a date close at hand), High from 6.5, Info below. The steps are shown on each notice under "Why these tags and score?". Because dates move scores, they are worked out each time notices are served, not stored.

The format also comes from the source's own category and the title alone, every time. Consultation conclusions and responses are not counted as open consultations, nor are SEC rule filings by exchanges. The Consultations card counts only consultations still open for comment and shows how many have closed.

The score does not know how much a notice matters to a particular firm, and is not a legal assessment.

## Checks

- **Dates:** `tests/dates.test.ts` checks the date rules on sentences from real notices, including ones that used to be given the wrong date.
- **Tests** (`npm test`, in `tests/`): each source's reader is run against saved copies of that source's real responses, so a change that breaks how a source is read fails the test. Tagging rules are tested against hand-labelled notices (see "Sectors and formats"). The impact rubric is tested the same way (`tests/impact.test.ts`), and every source's notices are checked to carry the rubric's reasons. GitHub runs the type check, the tests and the build on every push (`.github/workflows/ci.yml`), except one that changes only Markdown files (the status log, these docs), which Vercel does not build either. A separate job audits the site's dependencies for known high or critical vulnerabilities (`scripts/ci-audit.sh`); when npm's audit service does not answer, it tries again up to three times, a minute apart, and a report of vulnerabilities fails at once. `tests/ci.test.ts` checks both.

## Ground rules

- No firewalls are bypassed. Where a source blocks cloud servers, the site uses another page the regulator publishes.
- Requests are spaced out to stay polite to the regulators' sites.
- There is no sample or made-up data. If a source fails, the last good data is kept and the error is shown.

## Deployments and storage

Every push builds a deployment (a preview for a branch, production for `main`), and Vercel keeps each one's copy of the API function until its retention period ends. Their total is the project's Functions Storage, which on the Hobby plan has a 10 GB allowance; in October 2026 it reached 9.1 GB, from 236 kept deployments of about 41 MB each, two thirds of them for commits that changed only the project log. Two settings in `vercel.json` keep it down:

- **`includeFiles`** adds the OCR files Vercel's tracing misses, and only those OCR loads: the English model `4.0.0_best_int` and the Tesseract engine builds for Node, as `.js` and `.wasm` (not the `.wasm.js` copies made for browsers, nor the larger `4.0.0` model). tesseract.js 7 loads the builds without "-lstm" in Node even in LSTM mode (it compares a true/false flag with the mode numbers), so both kinds are kept. This brings the OCR files from 31 MB to 12 MB compressed, about 22 MB a deployment in all. `npm test` checks that every build tesseract.js can load and the model are included, and reads a sample image by OCR.
- **`ignoreCommand`** skips the build when nothing but Markdown files (`*.md`) has changed since the branch's last successful deployment (`VERCEL_GIT_PREVIOUS_SHA`). A merge that brings code and ends with a log update is still built, as are a redeploy of the same commit, a branch's first deployment, and any case where the last deployment's commit is not in Vercel's clone. `npm test` runs the command in a scratch repository for each case.

Old deployments are deleted by the project's deployment retention policy (Project → Settings → Security). Vercel always keeps the deployment serving the site and the last three production deployments, and a deleted deployment can be restored for 30 days (Settings → Security → Recently Deleted).

## Security headers

`vercel.json` sends a Content Security Policy with every response: scripts only from the site itself (plus the one inline script in `index.html` that sets the theme before the page draws, allowed by its hash), styles and fonts only from the site and Google Fonts, no framing by other sites, and no plugins. It also sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a `Referrer-Policy` that sends other sites only the origin, and a `Permissions-Policy` that turns off camera, microphone and location. A test fails if the inline script changes without its hash. The server does not send `X-Powered-By`.

The icon font is loaded with only the icons the page uses (`icon_names` in `index.html`, about 13 KB instead of 4 MB), and nothing is drawn until it arrives, so icon names never show as words. A test fails if the page uses an icon that is not in the list.
